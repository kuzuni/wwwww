# HP 타격감 3차 채점 메모 — 다음 3D 세션 인계

세션 결과: **SKIP_3D로 종료** (구현 착수 안 함). 이 파일은 채점 근거만 남긴 것이다.

## 왜 SKIP_3D인가
시작 시 컨테이너 클론이 **원격과 공통 조상이 없는 낡은 8커밋 라인**을 가리켜, 가드가
"최신 3D 마커 15분 전"으로 오판해 작업을 시작했다. 실제 원격에서는 다른 3D 세션이 같은 항목
(`HP 깎이는 연출 최대한 쥬시하게`)을 이미 2회 채점(3.5 → 4.5/10)까지 진행 중이었고,
push 거부 → `pull --rebase` 시 충돌로 드러났다. 재확인 시 8분 전 다른 `[3D작업중]` 클레임이
있어 가드 규칙대로 종료했다. **가드의 10분 창을 60~120분으로 늘리고, 시작 시 `git fetch`로
원격 tip을 강제 확인할 것** — 같은 원인으로 이 항목이 두 번 중복 구현됐다(987fe5a 인계 메모도 동일 지적).

## 3차 채점 결과 (비평가 B, 독립)
**5.5 / 10 — 불통과** (게이트 9.0). 항목별: 2단 HP바 6.5 / 피격 반응 5.5 /
데미지 숫자 6.5 / 처치 버스트 3.5 / 영웅 비네트 3.0.

### ⚠️ 이 채점의 방법론적 한계 (반드시 감안할 것)
채점 도중 이 세션이 `git reset --hard origin/main`을 실행해 작업 트리가 바뀌었다. 그 결과
비평가가 본 것은 **혼합 기반**이다:
- **스트립(그림)** = 이 세션의 옛 빌드(fa8e3ca 이전 base + 바 블룸 오버레이 수정).
- **코드** = 현재 main(fa8e3ca 이후, `driveHpBar`/`impactFlare`/`sev` 체계).
따라서 그림 근거 지적은 **현재 main 기준으로 재캡처해 재확인**해야 하고, 코드 근거 지적은
그대로 유효하다. 아래에 그 둘을 분리해 뒀다.

## A. 현재 main에서 코드로 직접 확인한 결함 (재캡처 없이 착수 가능)

| 확인 | 위치 | 내용 |
|---|---|---|
| ✅ | `js/combat.js:241,249` + `js/scene3d.js:3995` | **마지막 한 방에서 HP바가 같은 틱에 삭제된다.** `damageEnemy`가 `hitEnemy` 직후 같은 틱에 `killEnemy`를 부르고, `killEnemy`가 `m.hpBg.parent.visible=false`를 즉시 실행 → HP가 0으로 빠지는 장면이 **한 프레임도 렌더되지 않는다.** 이 항목에서 가장 쥬시해야 할 이벤트가 화면에 없다. 수정: 바 숨김을 ~0.28s 지연하고 그 사이 `driveHpBar`가 0까지 구동되게 할 것 |
| ✅ | `js/scene3d.js:3952` | `if (crit || sev > 0.1)` 게이트 때문에 **일반 잡타(sev ≤ 0.1)에는 히트스톱·스쿼시가 전혀 없다.** 연타가 3번의 충격으로 분리되지 않는 원인. 수정: 게이트 제거하고 sev 비례 최소 프리즈(≈0.018s) 상시 부여 |

## B. 그림 근거 지적 — 현재 main으로 재캡처 후 재확인 필요
1. **임팩트 프레임이 형태 없는 흰 덩어리** (1순위 지적). `impactFlare(0.95)`+`(1.25)` additive가
   `flashMesh` 0.28로 아낀 밝기 예산을 다시 태워, 히트스톱 45ms으로 정지시킨 그 프레임에
   스쿼시·롤·넉백·파편이 전부 블룸에 묻힌다. 제안: 플레어 크기 0.5/0.62·수명 0.08/0.1로 축소,
   flareTex를 방사 글로우 → 초승달+예각 스파이크 마스크로 교체.
2. **처치 버스트의 충격 링·파편 12개가 어느 프레임에도 안 보임** (2순위). 링은 얇은 애뉼러스로,
   파편은 플레어와 명도 분리 + 모션 스트레치. 처치 순간 주변 40ms 감광으로 대비를 만들 것.
3. **영웅 머리 위 2단 바가 D 스트립 18프레임 전체에 없음** (3순위). json은 heroFg 0.42 /
   heroGhost 1.0인데 화면에 없다 → 크롭 문제인지 렌더 문제인지 먼저 규명할 것.
4. 앞바 자체 모션 0(컨테이너 펀치 없음), 민트/주황 seam 무장식, 흰 플래시가 앞바 전체를
   110~140ms 덮어 잔량·등급색 판독 불가, 크리 위계가 크기 15%+색뿐, 데미지 숫자가 340ms 동안
   opacity 1로 정지 체류.

비평가 총평: 남은 문제는 대체로 **"밝기로 해결하려 한 것을 형태로 바꾸는" 작업** +
**바 자신의 모션 어휘(펀치·seam 하이라이트·이징 테일) 추가** + **처치/영웅 두 케이스의 구멍 메우기**.
반대로 설계가 옳다고 평가된 자산: 2단 바 규약(홀드 210ms/추격 200ms는 원신 대역),
연타 누적 유지(잔상 고정 + 앞바 계단 하강), 프리즈 해제 첫 프레임에 숫자 띄우기,
임팩트 프레임에 넉백 선반영, `flashMesh` 0.28 캡 판단.

## C. 이 브랜치(`3d/hpbar-bloom-overlay`)에 든 것
현재 main에 **머지되지 않은** 실험 1건: HP바를 블룸 패스에서 아예 제외하고 포스트 합성 뒤에
오버레이로 얹는 방식(`BAR_LAYER` + `renderBarOverlay`). main의 접근(채움색을 블룸 임계 아래로
낮추기 + 어두운 배경판 + `toneMapped:false`)과 **목적이 같아 대부분 중복**이지만, main 방식은
**옆 스파크의 블룸 번짐**까지는 막지 못한다(블룸은 스크린 스페이스 블러라 바 자신의 색과 무관하게
이웃 밝기가 번진다). 위 B-1(플레어 축소)을 먼저 적용한 뒤에도 바가 여전히 씻긴다면 이 오버레이를
검토할 가치가 있다. 그 전에는 채택하지 말 것 — 중복 복잡도만 는다.
